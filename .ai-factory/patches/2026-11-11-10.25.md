# Ревью E4: изоляция setLocal, afterCommit, попытка идемпотентности, очистка на соединении блокировки, тесты без пауз

**Date:** 2026-11-11 10:25
**Files:** src/database/db.ts, src/database/run-exclusive.ts, src/database/batches.ts, src/database/index.ts, src/idempotency/idempotency.interceptor.ts, src/idempotency/kit-idempotency.module.ts, src/idempotency/table.ts, src/internal/pg-errors.ts, src/cli/commands/db.ts, src/testing/tenant-isolation.ts, src/observability/metrics.ts, test/fixtures/database/migrations/0004_*, test/consumer/minimal/drizzle/0002_*, тесты I
**Severity:** medium

## Problem

Ревью E4 (KT-21/KT-22) нашло восемь дефектов. `Db.setLocal(tx, 'app.tenant', …)` проходил проверку имени и мог сменить тенант посреди транзакции. `Db.afterCommit` с чужой или вложенной транзакцией молча терял задачу. Долгий первый запрос с ключом идемпотентности затирал ответ повтора, который перехватил строку через 5 минут. Очистка идемпотентности при `DB_POOL_MAX=1` каждый час падала с `error`. Проход очистки, прерванный остановкой, считался `ok`. CLI `db` терял `sqlState` из `cause` у `DrizzleQueryError`. `assertStrictTenantIsolation` брал первую попавшуюся перегрузку `idempotency_purge`. В тестах были реальные паузы (`setTimeout`, опрос).

## Root Cause

- Проверки строились по форме входа, а не по смыслу. Регулярка имени `app.*` не отделяла служебные переменные пакета. `afterCommit` проверял только read-only, но не принадлежность транзакции этому `Db`.
- Хранилище идемпотентности опознавало строку только по области и ключу. Переиспользование брошенной `in_progress` меняло владельца строки, а метки владельца не было.
- Внутри `runExclusive` вторая операция брала второе соединение того же пула, хотя первое уже было выдано и держало блокировку.
- Итог прохода выводился из двух состояний (`complete` и предел пачек), третье (остановка) не различалось.
- CLI читал `code` только с верхнего уровня ошибки, без обхода `cause`, который уже был в `pg-errors`.
- Каталог читался по имени функции, без сигнатуры, которую проверяет модуль при старте.
- В тестах сигнал «операция началась» заменяли паузой.

## Solution

- `RESERVED_LOCALS` (константа, сейчас `app.tenant`): `setLocal` с таким именем бросает `TypeError`.
- `AfterCommitOutsideTransactionError`: `afterCommit` с дескриптором не из `transactions` этого `Db`.
- Колонка `attempt uuid not null default gen_random_uuid()`. `begin` ставит новую метку при вставке и при переиспользовании, `complete` и `release` пишут с условием `attempt = <своя>`. Если `complete` обновил 0 строк — `warn` без ключа и тела, повтора нет.
- `runExclusive` передаёт в `fn` клиента блокировки. Внутренний `transactionOn(db, client, ctx, fn)` выполняет транзакцию `Db` на выданном клиенте, `deleteInBatches({connection})` — тоже. Очистка идемпотентности выполняет пачки на соединении блокировки.
- `resultOf(complete, batches, maxBatches)`: `ok` / `partial` / `interrupted`. Алерт по-прежнему смотрит только на `error|partial`.
- `sqlStateOf(error)` в `internal/pg-errors.ts`: обход `cause` до 10 уровней, только SQLSTATE с цифрой. Коды Node вроде `EPIPE` отсекаются.
- `purgeViolations` ищет функцию по `to_regprocedure('"<схема>".idempotency_purge(integer)')`.
- Тесты I: `nextEntry()` и `closeGate()` в стенде идемпотентности, `once(pool, 'acquire')`, сигнал отправки запроса `idempotency_purge`, шлагбаум внутри `fn` у `runExclusive`.

## Prevention

- Служебные переменные и метки пакета держать в одной константе. Публичные API, принимающие имя, должны проверять её явно, а не только формат.
- Любая запись «результата операции» в разделяемую строку — с меткой владельца (попытки), если строку могут переиспользовать.
- Внутри функции, которая держит соединение пула, давать вызываемому коду это соединение. Тест при `DB_POOL_MAX=1` ловит такие deadlock-и пула.
- Метрика итога фоновой задачи должна различать каждое состояние выхода. Таблица итогов — в TSDoc метрики.
- Коды ошибок драйвера искать обходом `cause`: обёртки ORM держат исходную ошибку там.
- Проверки по каталогу PostgreSQL — по сигнатуре (`to_regprocedure`), а не по имени.
- Регрессионный тест подтверждать падением без правки (`git stash` правки → тест красный → вернуть). Однажды тест падал по посторонней причине: у журнала миграций метка `when` была меньше уже применённых, и миграцию пропускали.
- В тестах ждать сигнала (промис входа, событие пула), а не времени.
