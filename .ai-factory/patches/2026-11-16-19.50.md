# sanitizeError не распознавал настоящий DrizzleQueryError без pg-причины

**Date:** 2026-11-16 19:50
**Files:** src/observability/sanitize-error.ts, test/unit/observability/ac-2-3-sanitize-error.spec.ts, test/unit/observability/ac-2-5-sentry-scrubber.spec.ts, test/unit/observability/ac-2-16-background-failures.spec.ts, alerts/verdeect-kit.rules.yml, test/fixtures/alerts/verdeect-kit.test.yml, CHANGELOG.md
**Severity:** high

## Problem

KT-124 (находка Identity ID-70): ошибка Drizzle без кода PostgreSQL (тайм-аут запроса, обрыв соединения) уходила в лог и GlitchTip с текстом SQL и значениями параметров («Failed query: <SQL>\nparams: …») — нарушение §3.2 и NFR-4.

## Root Cause

`isDrizzleQueryError` проверял только `name === 'DrizzleQueryError'` (и `type` сериализованной формы). В drizzle-orm 0.45.4 класс `DrizzleQueryError` не задаёт `name`, у экземпляра `name = 'Error'`. С pg-причиной дефект был скрыт: ветка срабатывала по pg-звену в `cause`. Тесты строили подделку `Object.assign(new Error(…), {name: 'DrizzleQueryError'})` — она описывала предположение о библиотеке, а не саму библиотеку, поэтому проходила.

## Solution

Распознавание по форме экземпляра: строковое `query` и массив `params`, или `constructor.name === 'DrizzleQueryError'`, или `type` сериализованной формы. Импорта drizzle-orm в `src` нет. Результат прежний — `SanitizedDbError` «Failed query» (+ code причины). Тесты AC-2.3, AC-2.5, AC-2.16 — на настоящем `new DrizzleQueryError(...)` из drizzle-orm (dev-зависимость), с pg-причиной и без неё.

## Prevention

- Распознавание ошибок сторонних библиотек «по форме» проверять тестом на настоящем экземпляре класса библиотеки (dev-зависимость), а не на подделке с ожидаемыми полями.
- `name` — не форма: многие библиотеки его не задают (остаётся `'Error'`); надёжнее собственные поля экземпляра.
- Ветка очистки должна срабатывать без вложенной причины: у тайм-аута и обрыва соединения SQLSTATE нет.
